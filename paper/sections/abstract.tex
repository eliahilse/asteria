\begin{abstract}
When LLMs (Large Language Models) generate code, the security of the
output depends on what the model knows about the existing program. This
paper studies \emph{security context}: assets, trust boundaries, weakness
types, requirements and controls that a planned change touches, passed in
the prompt before the model writes. The task is a Highscore feature for a
Java game, implemented from scratch (Generation) or by reusing a sibling
game's implementation (Reuse); ten security checks and sixteen functional
tests score every artifact, and every arm is compared with a control
collected alongside it. Context written by a researcher lowers the number
of failed security checks in all 18 context arms of two rounds. Context
acquired by an agent from the repository, a one-line feature description
and a vocabulary lowers it further but at first costs functionality; an
audit traces the loss to one sentence about a player without a name, and
two revisions of the agent's instructions remove it: failed checks fall
from 39 to 11 of 50 in Generation and from 31 to 7 in Reuse with every
artifact functional, reproduced by two further acquisitions. Under one
response without feedback, three acquisition strategies fail 3, 17 and 10
checks of 250 against 101, 77 and 94 for their controls. In agentic
delivery with feedback, at five trajectories per cell, the document cuts
failed checks from 57 to 12 of 100 with every artifact functional; a code
graph of what the model reads adds nothing measurable, a judge that
cancels a violating submission removes a few more failures at twice the
calls, and an advisory judge adds submissions, not security. One task, one pair of games and
two to five artifacts per arm limit what the counts can claim.
\end{abstract}
