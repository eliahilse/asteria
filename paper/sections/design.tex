\section{Study Design}
\label{sec:method}

\subsection{Task}
The task is a Highscore feature for the game ApoMario: record a finished
run's score, player name and survival time, keep the records in a file
across sessions, and show them sorted in a menu panel. In the
\emph{Generation} variant the model sees only ApoMario; in the \emph{Reuse}
variant it also sees the sibling game ApoIcarus, which has a Highscore
feature, and is asked to reuse it. Task text, target and donor games and
the functional test suites are those of the prior study. The threat model
is a desktop game: the untrusted inputs are local files the user can edit,
level content from a shared server, and in-game values a player can tamper
with to cheat.

\subsection{Harness}
The model receives the task, the base-context files of its cell and, in a
context arm, the security context appended after the task. It answers with
new classes and exact edits to three existing files, delivered through a
tool call. We call one such conversation a \emph{trajectory} and its final
code the \emph{artifact}. Three delivery modes are used.

\paragraph{One-shot.}
One response, no feedback: the protocol of the prior study (rounds I22 to
I25). Delivery is \emph{strict} by default: a returned file that names an
existing file is rejected as a delivery error, an edit anchor must occur
exactly once, and the three target files must differ from the originals.
Because a rejected response never reaches the compiler and the prior
study's pipeline writes every returned file before compiling, the one-shot
baseline is also collected under \emph{lenient} delivery, in which a
returned file that names an existing file replaces it whole; edit anchors
stay exact. Which mode a round used is declared in its plan.

\paragraph{Submit with feedback.}
The mode of rounds I03 to I21b: after each submission the model receives
the compiler's diagnostics and the outcome of the sixteen functional tests,
and may submit up to five times in total. No repository tools. An artifact
is \emph{functional} when it passes all sixteen tests within the budget;
the first-submission count is reported alongside because it is the
one-shot-comparable number.

\paragraph{Agentic.}
The model may search and read the repository through the same tool before
submitting, under a budget of tool turns. A \emph{sidecar} can act on the
trajectory: inject the statements relevant to the code just read or edited
(adaptive), or judge a submission that edits an enforcement point and
reject it, attach advice, or rewind the conversation (gate variants,
Section~\ref{sec:results}).

\paragraph{Guard sidecar (judge).}
The sidecar used for the agentic rounds of the next series runs
\emph{before every tool call}, not only on submissions. The judge, the same
model in a separate conversation, receives the task, the security context,
a compact trace of the trajectory so far, the pending action with its
arguments and the model's visible message text for that turn (the provider
does not return hidden reasoning; when no text is available the record says
so). It may itself read and search the repository for a bounded number of
turns, then must answer with a verdict: intervene or not, with the
statements it cites and advice. On intervention the pending call is not
executed; the generator receives the advice and the cited statements as
the tool result, marked as coming from the guard, and continues. A cap on
interventions per trajectory and a shadow mode that records verdicts
without acting allow the judge to be calibrated before it is let act.
After its first round the judge is consulted on submissions only, and a
verdict acts only if it cites at most two requirement or control
statements, quotes at least one submitted line verbatim, and names a
statement the guard has not already cancelled for in that trajectory. An
\emph{advisory} variant never cancels: the submission executes, a positive
verdict rides on its compiler and test feedback, and a functional
submission with a positive verdict continues the trajectory instead of
ending it. Every judge request and response is recorded with the
trajectory.

\paragraph{AST autocontext.}
A second sidecar for the agentic rounds helps with the code rather than
with security. The repository snapshot is parsed once into a code graph:
every class, constructor and method with its file and line range, and the
resolved call edges between them. After each read the sidecar appends to
the tool result, for every method the read lines overlap that was not
shown before, its callers and callees with the path and line range the
generator can read next, bounded to six symbols and four thousand
characters per injection. It contains no security statement and makes no
model call. An arm may combine the static insert, this sidecar and the
guard (for example all three), so the security effect of the judge and the
functional effect of the graph can be separated.

The same model (Luna) serves as acquisition agent, generator and judge; its
served identity is recorded per response, sampling settings are requested
per round (reasoning effort medium for rounds up to I22, high from I23 on)
and are not attested by the provider. Every round is declared and frozen
before its first model call, has its own fresh control arm collected at
the same time, and is completed regardless of direction. Time and tokens
(input, output, reasoning) are recorded for every model call and every
acquisition and reported per arm.

\subsection{Context}
Base context is what the prior study varied: structural (S), functional
(F) and behavioural (B) descriptions of the target game, alone or combined,
or none. A \emph{cell} is a task variant with one such combination. Round
I23 reran all sixteen cells with our generator under the one-shot protocol
(Table~\ref{tab:matrix}); the cells with the most functional artifacts on
one response, Generation None, S and S+F+B and Reuse F and S+F+B, are the
cells of the one-shot security rounds. Round I25 repeated the matrix under
lenient delivery and moved single cells by up to three of five, so the
choice rests on one rerun and every security round keeps its own control.
The earlier rounds used Generation S, Generation S+F+B, Reuse B and Reuse
S+B.

\subsection{Security Context}
\paragraph{Generation.}
Security context is produced without a person who knows the code. The
acquisition agent receives a one-line task sentence (the feature and the
target), the vocabulary of Section~\ref{sec:related} as an output schema
with CWE, CAPEC and ASVS identifiers, and, depending on the strategy, a
read-only snapshot of the repository (for Reuse, of both games). It
receives no test, no threshold, no earlier context and no generated code.
It inspects what it is given with shell tools~\citep{yang2024} under a
recorded command budget and writes one typed document. Every statement
that cites code is checked: the harness resolves each citation against the
parsed code and drops statements whose citations do not resolve, which
validates that the cited code exists, not that the statement is right.
Statements carry a one-line \emph{failure behaviour}, what the code should
do when input is invalid; the agent's instructions were revised twice
about it (versions 9 and 10, Section~\ref{sec:results}) and three times
about bounds (version 11: a bound is a concrete number kept by evicting
or truncating what exceeds it, never by rejecting a valid input, and the
domain of each validated value is stated; version 12: the domain of a
text names presence, blankness after trimming and a length; version 13:
each unit read from untrusted data is bounded in bytes or characters). The document is
rendered as text and appended once after the unchanged task, either in
full (assets, trust boundaries, then every statement) or as a
\emph{compact insert} of requirement and control statements only.

\paragraph{Cases.}
Three strategies are paired with the base contexts in the one-shot rounds:
\begin{enumerate}\setlength\itemsep{0pt}
\item \emph{High-level guidance} (S1): the agent reads the repository but
  writes general rules for this kind of feature in this kind of program,
  naming operations by their role and citing no code.
\item \emph{Full document} (S2): the data-flow angle (trace untrusted data
  from where it enters to where it is stored, enumerate STRIDE threats,
  place requirement and control where the data first arrives), rendered in
  full with every statement anchored to code.
\item \emph{Generic} (S3): no repository at all; context written from the
  language, the kind of program and the task sentence.
\end{enumerate}
The earlier rounds also used researcher-written inserts (operations,
requirements, trust boundaries), a one-sentence generic instruction, the
flat CWE Top~25 list~\citep{cwetop25}, two further agent angles
(requirements, catalogue) and the compact renderings. The agentic rounds
(I26 to I28) use S2 alone, with and without the code graph and the two
judges; rounds I29 to I31 repeat the agentic comparison with data-flow
documents acquired under the version 11, 12 and 13 instructions.

\subsection{Security Evaluation}
Every final artifact runs the ten security checks of
Table~\ref{tab:mapping} in an isolated Java virtual machine with a 64~MiB
heap and a 15~s limit per check, plus a persistence round trip reported
separately. The checks: the store rejects a negative score, a negative
survival time, a missing name, a blank name and an over-long name (five
input-policy checks; a record must be refused, normalising it counts as
a failure because the contract fixes rejection as the policy); at most one
hundred records are retained after more are stored; a corrupted store file
does not crash the game; a single line of 64~MiB and a store of one million
records do not exhaust memory (two resource checks); and no Java object
deserialization is used for the store. A check passes, fails, or is
\emph{unresolved}: the artifact was rejected at delivery or did not
compile (then all ten are unresolved), the check could not run, or its
precondition was unmet (the million-record check needs a file format the
generator can write). A safe and a deliberately weak reference
implementation must produce the expected outcomes before every run.
Beyond the checks, every final artifact's run-end method is audited for
how it treats a player without a name (Section~\ref{sec:results}), and
every reviewer classification cites the lines it rests on.

\subsection{Functional Evaluation}
Sixteen functional tests from the prior study score each submission:
seven unit tests of the store, four integration tests that call the
feature from real game objects, and five autonomous tests that end a run
in the live game and inspect the board. We report, per arm with $N$
trajectories: delivered (the response was accepted by the delivery
protocol), compiled, functional (all sixteen tests pass) on the first
submission and within the budget, and for the security checks the number
failed, unresolved and passed out of $10N$. All numbers are counts over
fixed denominators; no percentages are printed below twenty trajectories.
A difference to the control is given as an identification bound: the
smallest and the largest difference obtainable by resolving each arm's
unresolved checks as passes or as failures; no confidence intervals and no
significance claims. Per-check outcomes for every arm, spreadsheets with
every trajectory, and the artifact reviews are in the study repository.
