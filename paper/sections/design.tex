\section{Study design}
\label{sec:design}

\paragraph{Corpus and task.}
Apo-Games is a family of Java and Android games maintained by
clone-and-own~\citep{krueger2018}. The target, ApoMario, receives a Highscore feature with a fixed public API (a
store constructor, \texttt{storeRun}, three list accessors, persistence, and
run-end recording in the game). In \emph{Generation} the generator sees only
the target; in \emph{Reuse} it also sees ApoIcarus and must reuse its
Highscore feature. Structural (S), functional (F) and behavioural (B)
context files define four cells: Generation S,
Generation S+F+B, Reuse B, Reuse S+B.

\paragraph{Model and delivery.}
One model serves as agent and generator. Each trajectory is one conversation:
the generator delivers new classes and exact edits to three target files
through a tool call, receives compiler diagnostics and the outcomes of 16
functional checks (7 unit, 4 invoked, 5 autonomous), and may resubmit up to
five times. Security feedback is never returned. Served model identity is
checked per response; sampling settings are requested but unattested.

\paragraph{Security evaluator.}
Eleven checks run per artifact in isolated JVMs (64~MiB heap, 15~s): a
positive persistence round trip and ten issue checks (Table~\ref{tab:mapping}).
A safe and a deliberately weak control implementation must produce the
expected outcomes first. A two-record precondition audit
qualifies large-record outcomes; unsupported encodings are \emph{unknown},
never passes.

\paragraph{Reporting.}
Rates are counts over fixed denominators: $N$ trajectories per cell and arm,
$N$ per issue check, $10N$ for the ten issue checks. Unresolved outcomes
(non-compiling artifact, unknown, not run) remain in the denominator as a
separate count. Differences between context arms and controls are
identification bounds over every assignment of unresolved
outcomes, not confidence intervals; no significance claim is made.
