Security context for implementing ApoMario highscore. The donor provides a remote singleton highscore with parallel mutable lists and a UI sorting/rendering pattern, while ApoMario exposes actual player points and level elapsed-time-related APIs at run completion. The requested implementation must adapt—not blindly copy—the donor persistence and networking model to the required Path-backed local store and public API.

[recommendation; task; input validation] At the storeRun boundary, validate score and survivalTime as bounded non-negative values, reject null/blank or excessively long playerName, and define handling for control characters and malformed Unicode before inserting or displaying data. This guard belongs in ApoMarioHighscore.storeRun because names and numeric values are externally supplied to the public API and later rendered in a menu view; verify with null, blank, oversized, control-character, negative, and extreme-value cases.
Task relevance: The task requires recording a player name, score, and millisecond survival time and exposes storeRun publicly.
Basis: prospective task requirement or reasoning; not a claim about implemented safeguards.
Suggested verification: Unit tests assert invalid records are rejected without changing any of the three lists or the store.

[recommendation; task; local persistence safety] Implement the Path-backed store as a bounded, versioned record format with strict parsing, size/entry-count limits, and safe failure behavior. Persist via a temporary file in the store directory followed by an atomic replace where supported; avoid exposing partially written data. Enforce these guards during construction/load and persistAcrossRuns, and verify truncated, malformed, oversized, and unavailable files leave valid in-memory data intact and do not throw into the game loop.
Task relevance: The required constructor receives a file Path and the board must persist across runs.
Basis: prospective task requirement or reasoning; not a claim about implemented safeguards.
