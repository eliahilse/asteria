Generic security context for a Java desktop game's achievement tracking, local persistence, and menu display. No repository was available for inspection.

Assets:
- Achievement records [integrity]
- Game availability [availability]
- Achievement data handling [resistance]

Trust boundaries:
- Running-game progress [entry point]: Points, enemy counts, and survival durations produced or tampered with during gameplay from Running game state and local cheating attempts to Achievement progress and unlock evaluation
- Local achievement store [entry point]: User-editable persisted achievement records and file contents from Local filesystem to Achievement store parser and loader
- External level content [entry point]: Level data loaded from a shared level server or other external source from Outside the program to Level parser and gameplay integration

[R1; requirement; task; tampering; CWE-20; CAPEC-20] The operation that receives achievement progress or run-finalization values shall accept only non-negative integers for points, enemy counts, and elapsed milliseconds, and shall reject and report values outside that domain without substituting or clamping them.
Task relevance: Protects threshold evaluation from malformed or tampered gameplay inputs.
Failure behavior: Reject and report the invalid value; the gameplay integration caller shall normalize missing or invalid progress to the stated non-negative default before invoking the operation so gameplay achievement tracking continues.
Basis: prospective task requirement or reasoning; not an implemented safeguard.

[R2; requirement; reasoned; denial_of_service; CWE-400; CWE-789; CAPEC-130] The achievement store shall read untrusted files using bounded units: no more than 64 KiB per line, 256 KiB per record, and 1 MiB total per store read; data exceeding a bound shall be rejected and reported.
Task relevance: Prevents oversized local files from exhausting memory or blocking startup.
Failure behavior: The parser rejects and reports the oversized unit; the loading caller uses an empty achievement set before calling the parser so the game and achievement feature remain available.
Basis: prospective task requirement or reasoning; not an implemented safeguard.

[R3; requirement; reasoned; elevation_of_privilege; CWE-502; CWE-913; CAPEC-586] The persisted achievement format shall be explicit data such as bounded text or structured records and shall not use Java object deserialization or execute code represented by store contents.
Task relevance: Ensures saved achievement records cannot trigger code execution when loaded.
Failure behavior: The receiving decoder rejects and reports unsupported executable or serialized input; the caller initializes an empty achievement set before decoding so normal gameplay and unlocking still work.
Basis: prospective task requirement or reasoning; not an implemented safeguard.

[R4; requirement; task; denial_of_service; CWE-248; CWE-703; CAPEC-吹] Malformed, unreadable, or semantically invalid achievement-store contents shall not prevent the game or menu from running; the load integration point shall substitute an empty unlocked-achievement set before requesting parsing or display.
Task relevance: Preserves availability while allowing achievements to unlock and be saved after recovery.
Failure behavior: The store operation rejects and reports the malformed input, while its caller uses the empty set and continues the primary game/menu operation.
Basis: prospective task requirement or reasoning; not an implemented safeguard.

[R5; requirement; reasoned; denial_of_service; CWE-400; CAPEC-130] The retained unlocked-achievement collection shall be bounded to the three defined achievement identifiers, and any additional records shall be evicted or omitted from retained and displayed state rather than causing an otherwise valid defined achievement to be rejected.
Task relevance: Keeps persistence and the dedicated menu panel small and predictable.
Failure behavior: The collection bounds operation evicts unsupported excess records and reports the condition; the caller retains the valid defined achievements and continues displaying the panel.
Basis: prospective task requirement or reasoning; not an implemented safeguard.

[R6; requirement; task; tampering; CWE-345; CWE-20; CAPEC-472] Run progress shall be reset at each run start, evaluated against the actual level values at run end, and unlocked identifiers shall be persisted only as the defined POINTS_GOAL, ENEMIES_GOAL, and TIME_GOAL values once their thresholds are reached.
Task relevance: Prevents progress carrying across runs and preserves correct unlock integrity across sessions.
Failure behavior: The progress evaluator rejects inconsistent or unsupported identifiers and reports them; the gameplay caller starts from zero-valued run state and still performs the run-end evaluation and save operation.
Basis: prospective task requirement or reasoning; not an implemented safeguard.
